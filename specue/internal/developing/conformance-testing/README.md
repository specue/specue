Команды проверяются интеграционными тестами, выведенными из решений,
независимо от реализации: тест проверяет контракт и зафиксированные
ожидания, а не конкретный код. Реализация корректна, если проходит набор.

## Чем реализовано

Go-харнесс на `github.com/rogpeppe/go-internal/testscript`. Каждый
сценарий — файл `testdata/<имя>.txtar`: инлайн-фикстура модуля
(`-- cue.mod/module.cue --` и т.п.) + команды-проверки. Внутри скрипта
имя `specue` означает тестируемый бинарь.

## Как запускать

```sh
mise run conformance   # сборка бинаря + прогон на пиннутых go/cue/jq
```

Вручную, против любой реализации:

```sh
SPECUE_BIN=/path/to/specue \
SCHEMA_DIR=/abs/path/to/cue/schema \
go test ./...
```

- `SPECUE_BIN` — путь к тестируемому бинарю; не задан → тесты skip;
- `SCHEMA_DIR` — абс. путь к `cue/schema` для offline-replace; не задан → fail;
- `cue` и `jq` нужны в PATH (валидация файлов / проверка JSON); нет → skip;
- резолв оффлайн: `CUE_REGISTRY=localhost:9999+insecure`, а команда
  `link-schema` дописывает в фикстуру `cue.mod/local-module.cue` с
  replace на локальную схему (`SCHEMA_DIR`).

## Что проверяет сценарий

Полный путь команды: вход (фикстура модуля + аргументы) → выход:
- код возврата (`! specue …` ожидает ненулевой);
- stdout/stderr-контракт;
- созданные файлы и их валидность по реальной схеме (`cue vet` — с
  зубами: кривой скелет валит проверку);
- КОНТРАКТ, а не подстроки: `jq -e` падает, если поле отсутствует или
  не той формы.

Каждый `.txtar` помечен решениями, которые покрывает (`# decision: <id>`),
чтобы покрытие решений тестами оставалось видимым.
