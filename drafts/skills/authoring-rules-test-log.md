# Лог проверки правил на переносимость

Метод: чужой субагент получает ТОЛЬКО прозу решения + правила (без
эталона, без указания результата). Выводит публичные обещания. Сравниваем
с нашим эталонным контрактом. Совпало → правило переносимо. Разошлось →
правило размыто, нужен операционный критерий.

## Прогон 1 (3 решения: понятие / процесс / составное)

**Сработало чётко (совпало с эталоном):**
- reject с кодами — все 3, коды точны;
- композиция reject у составного — собрал все коды из шагов;
- состав результата — уловлен.

**Поплыло → дописаны операционные критерии в правила:**
1. выход vs промежуточные шаги — агент потащил промежуточные результаты
   шагов в выход. → критерий «остаётся после завершения» (§1).
2. предел декомпозиции — агент слил двусоставную строку в одно поле.
   → критерий «независимо-опираемо» (§2).
3. форма факта — агент дал булево там, где есть значение (`hasName` вместо
   `name`). → критерий «значение→слот, свойство→булево» (§2).

**Тест поймал НАШИ нарушения (ценный побочный эффект):**
- входной аргумент оставлен публичным у нас — по §1 не должен;
- в контракт-понятие добавлены факты СВЕРХ прозы (README их не
  упоминает) — нарушение «строго из README». Решить: дописать прозу
  либо убрать из контракта.

## Прогон 2 (те же 3, дописанные критерии + правило открытых слотов)

**Закрылось (прогон1 → прогон2):**
- выход vs шаги: больше НЕ тащит промежуточные результаты — выход = что
  остаётся (граф). Критерий «остаётся после» сработал.
- форма факта: `name: string` вместо `hasName: true`, где есть значение.
- внешнее значение: открытые слоты `field: _` с пометкой «извне» —
  агент не выдумывает чужое (поля решения из пакета, тело и т.п.).
- вход-аргумент: помечен `path: _` как вход. Не путается с выходом.
- композиция reject: снова идеально (все коды из шагов).

Вывод: 3 из 4 дыр закрыты — независимый агент воспроизводит эталон по
структуре.

**Остаточный шум (на доработку правил):**
- декомпозиция «путь-в-пути» (контейнер/файл): агент то слил, то
  опустил — критерий «независимо-опираемо» к составному пути не
  применяет. Нужен явный пример именно про путь.
- граница «значение vs свойство» плывёт, когда значение приходит ИЗВНЕ:
  агент склонен к булеву (`hasIdentity: true`) вместо открытого слота
  (`identifiedBy: _`). Уточнить: внешний факт → всегда открытый слот,
  даже если «по смыслу свойство».

## Прогон 3 (правила про составной путь + внешнее→слот)

- внешнее значение → слот: ЗАКРЫТО. `identity: _` вместо `hasIdentity:
  true`. Композиция reject устойчива (теперь даже как дизъюнкция `|`).
- 5 из 6 критериев устойчиво воспроизводятся независимым агентом.

**Декомпозиция пути — НЕ дыра правил, а дыра ПРОЗЫ.** 3 прогона подряд
агент не дробит "cue.mod/module.cue" — потому что в прозе НЕТ факта, что
`cue.mod` это маркер корня. Мы вывели `rootMarker` из внешнего знания о
CUE (нарушение «строго из README»). Агент честно отражает написанное:
«объявлен в таком-то файле» = один факт. Чтобы дробление случилось,
проза сама должна сказать: «папка cue.mod/ отмечает корень; файл
module.cue в ней объявляет модуль» — два факта В ТЕКСТЕ.

ГЛАВНЫЙ ВЫВОД: правила переносимы и работают. Качество контракта =
качество прозы. Где мы переобещали сверх README (rootMarker,
dependsOnSchema) — агент не воспроизводит, и ПРАВИЛЬНО: правила +
честная проза дают тот же контракт; правила не чинят бедную прозу.

Следствие для проекта: контракты, где факты добавлены сверх README,
надо привести в соответствие — либо дописать прозу, либо убрать факт.
