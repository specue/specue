# Правила выделения публичных обещаний из прозы решения

Цель: из текстового описания решения вывести его публичный контракт по
чётким правилам, а не наугад. Правила абстрактны — примеры нейтральны и
не привязаны к конкретным решениям проекта.

---

## 0. Что такое публичное обещание

Контракт выражается на CUE. Публичные поля — то, на что СМОТРИТ и
ОПИРАЕТСЯ потребитель решения. (Приватные поля `_` — на что опирается
само решение; здесь не рассматриваются.)

Граница: всё, что решение отдаёт наружу — публично; всё, чем оно
пользуется внутри — не публично.

---

## 1. Что становится публичным

Публично — только РЕЗУЛЬТАТ (что решение даёт наружу), не процесс.

- **Для процесса** (что-то делает и завершается): ВЫХОД (что осталось на
  руках) + ИСХОДЫ-ОТКАЗЫ (`reject` с кодами).
- **Для понятия** (описывает сущность): ПРОВЕРЯЕМЫЕ ФАКТЫ этой сущности.

НЕ публично (внутренности «как»): конкретная команда/API, направление и
алгоритм действий, порядок и перечень шагов, промежуточные действия,
входные аргументы.

**Критерий ВЫХОДА:** выход — то, что ОСТАЁТСЯ ПОСЛЕ завершения решения
(финальный артефакт, который оно отдаёт). Промежуточные результаты шагов
исчезают по дороге и в контракт не идут. Тест: «это останется на руках у
потребителя ПОСЛЕ того, как решение отработало?» → да → выход. Перечень
действий/этапов в контракт НЕ переносится.

Тест на публичность: «потребитель это наблюдает / на это опирается?» →
публично. «Это про то, КАК сделано?» → внутренность.

---

## 2. В каком виде записывать факт

- **Один факт = одно поле.** Слитые ярлыки декомпозировать.
  **Предел декомпозиции:** дробить, пока на каждую часть можно сослаться
  ОТДЕЛЬНО. Критерий: «может ли потребитель опереться на эту часть саму
  по себе?» Да → отдельное поле.
  **Составной путь — всегда два факта.** Путь вида `A/B` («что-то ВНУТРИ
  чего-то») разбивай: `A` (контейнер/маркер) и `B` (элемент в нём) — это
  разные вещи, на каждую опираются отдельно. Не оставляй путь одной
  строкой и не выкидывай его как «процесс»: то, ГДЕ объявлено/лежит —
  это факт, а не действие.

- **Форма факта по смыслу.** Есть конкретное ЗНАЧЕНИЕ (имя, путь,
  идентификатор) → слот-значение (`name: string`, `id: "..."`). Чистое
  СВОЙСТВО/наличие → булево (`isFixed: true`). Не делать булевым то, у
  чего есть значение (булев `hasName: true` теряет само имя — бери
  `name: string`).

- **Смысловой факт, не строка-механизм.** Результат описывать тем, ЧЕМ
  он стал (`importable: true`), а не как строку-описание способа
  (`consumedBy: "import-by-version"`).

- **Источник значения: из прозы или извне.** Если значение поля задано
  самой прозой — пиши его. Если значение приходит ИЗ ДРУГОГО решения
  (проза говорит «по схеме X», «найденный Y», «то, что вернул Z»), его
  НЕЛЬЗЯ выдумывать или хардкодить — оставь ОТКРЫТЫЙ СЛОТ `field: _` с
  комментарием, ЧТО за внешний факт сюда встанет. Открытый слот честно
  говорит: «здесь значение из чужого знания, какого именно — здесь
  неизвестно». (Вход-аргумент решения — тоже открытый слот `field: _`:
  значение даёт вызывающий.)
  **Внешний факт → ВСЕГДА открытый слот, не булево.** Если решение лишь
  ПОЛУЧАЕТ что-то извне (своя идентичность, найденный объект, чужой
  результат), пиши `field: _`, а НЕ `hasField: true`. Булево — только
  для свойства, КОТОРОЕ УТВЕРЖДАЕТ САМА проза этого решения (например
  «версия фиксирована»), не для «у меня есть нечто из чужого знания».

- **Структуры закрывать** `close({...})` — чтобы лишнее/переименованное
  поле ловилось.

- Имена полей — английский lowerCamelCase; коды отказов — короткие
  строки.

---

## 3. Композиция (составные решения)

Если решение вызывает другие шаги (составное):

- его ИСХОДЫ-ОТКАЗЫ СКОМПОНОВАНЫ из отказов шагов — собираются вместе, а
  не хардкодятся заново;
- его ВЫХОД — финальный артефакт всей цепочки (по критерию §1), не
  выходы отдельных шагов.
